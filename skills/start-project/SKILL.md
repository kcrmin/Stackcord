# Start Project

Build durable product understanding before selecting implementation technology. Let conversation stay natural; use the CLI only for observable state and safe writes.

1. Resolve the CLI from `STACKCORD_CLI`, a repository build, or `PATH`, then run `stackcord status --json`. If no harness exists, treat that result as the starting diagnosis. On the first explicit product request only, an absent CLI may trigger an offer to run the matching verified `scripts/bootstrap-cli.sh` or `scripts/bootstrap-cli.ps1` with an explicit release URL, version, and install directory. Hooks never install software. If installation is unavailable or declined, use the repo-local fallback and disclose reduced verification.
2. Inspect files, Git, existing configuration, and detected tools before asking anything discoverable. When `CONTRIBUTING.md`, `AGENTS.md`, pull-request templates, issue templates, or an existing `.harness/git-conventions.yaml` define collaboration rules, use `$use-git-conventions` to preserve or reconcile them instead of replacing them with Stackcord defaults.
3. Treat the initial product request as the first material answer. Before asking the next question, and after every later material answer, normalize the complete current meaning. Use the valid input shape printed by `stackcord project checkpoint --help`, review the plan, apply it, and verify the successful apply before continuing. Save product summary, goals and non-goals, roles, journeys, capabilities, service policies, failure behavior, scenarios, quality, UI coverage, data needs, decisions, assumptions, and open questions. Never save raw dialogue or tone.
4. Recover saved decisions and discovery progress before asking. Group independent routine questions from the current section into one batch with 2–3 exclusive options labeled A/B/C for each question; put the recommended option first and mark it recommended. Preselect recommendations only as proposals in a supported question UI; they are not answers until the user submits them. Accept letters or free-form input. Ask dependent questions after their prerequisites are settled. Security downgrades, permissions, irreversible data actions, paid services and public releases always need explicit answers; never include them in bulk acceptance of defaults. Follow [discovery](../../references/discovery.md) for the checkpoint shape and progress report.
5. Surface important unconsidered security, privacy, abuse, accessibility, failure, operations, observability, support, and data-lifecycle cases at the point they can change a decision.
6. Keep technology undecided until product, quality, team, and operating constraints justify it. When a framework, task provider, design tool, database visualizer, CI system, or complementary workflow becomes useful, inspect installed tools first, search current official evidence when the choice can change, compare 2–3 realistic candidates, and explain their source-of-truth boundary. MengTo/Skills-like packages may be offered as optional UI creation help for reference analysis, interaction extraction, or prototyping; they never own the approved UI baseline, service meaning, or release identity. Connect only the user's choice; Superpowers, BMAD, Beads, Memory tools, GitHub, Jira, and future tools are optional complements rather than hidden dependencies.
7. Move from discovery draft to project setup only when existing product files already establish the boundary, or the first high-impact scope answer makes the target root clear. Then use `stackcord project init` for a new root or `stackcord project adopt` for an existing repository, review the plan before apply, preserve user files, and rerun combined status. Initialize collaboration Git early. When editable UI has independent ownership or history, review `stackcord git submodule add`, then use `stackcord workspace register` with `ui-baseline`; otherwise register an ordinary directory. Add a child boundary only when its ownership or lifecycle is genuinely independent.

After every answer batch, summarize the accepted choices and reasons, distinguish recommendations and unresolved blockers, and show the current section, completed/remaining sections, and approximate remaining-question range. Mark unknown estimates honestly. Tell the user when scope is sufficient to create the harness even if nonblocking discovery remains. Never repeat a settled question unless new evidence requires reopening it explicitly.

Example: for “결제 실패를 줄이는 서비스를 만들고 싶어,” inspect first and checkpoint known intent. Ask the unanswered product-boundary decision; once routine independent choices are known, group them and show progress instead of asking each in a separate turn.

Read [workflow](../../references/workflow.md), [safety](../../references/safety.md), [context recovery](../../references/context-recovery.md), and [tool selection](../../references/tool-selection.md).

On first explicit use after the project root exists, run `stackcord setup --json` to read the local UI preference. When no choice is recorded, offer the optional bundled local control center with explicit accept or decline. Accept runs `stackcord setup --ui enable --apply`; decline runs `stackcord setup --ui disable --apply`. Use the resolved root for all commands. Never treat silence as acceptance. Preserve `.harness/local/control-center.json` across Codex and Claude sessions; do not repeat the offer once decided. Later explicit enable/disable uses the same commands, and `stackcord setup --ui ask --apply` resets the preference on request. Launch `stackcord dashboard` only on request. No separate UI download is needed; disabling it preserves all project state and CLI capabilities. Never write durable project state into a plugin cache or host-specific plugin data directory. Both hosts read the same committed `.harness/`, `specs/`, `contracts/`, and local state and use CLI revision checks for writes.
